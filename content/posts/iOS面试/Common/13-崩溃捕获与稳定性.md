## 13.1 崩溃的本质：两条路

程序崩溃最终都走到**让进程死掉**，但路径分两种，采集方式完全不同：

```
路径 A：OC 异常（优雅崩溃）
  NSException（数组越界、KVO 未移除、nil 参数、unrecognized selector）
        ↓
  NSSetUncaughtExceptionHandler 可捕获 ✅（能拿到 callStackSymbols）

路径 B：Mach 异常 → BSD 信号（内存类崩溃）
  野指针 / EXC_BAD_ACCESS / 被 trap
        ↓ 内核 Mach exception
  （无 handler 时）转成 BSD signal（SIGSEGV、SIGABRT、SIGBUS…）
        ↓
  signal handler 可捕获 ✅（但拿不到栈，要自己逐线程回溯）
```

| 崩溃类型 | 触发例子 | 触发路径 | 可被哪个 handler 捕获 |
|----------|----------|----------|------------------------|
| **OC 异常** | `[arr objectAtIndex:999]`、KVO 未移除、`doesNotRecognizeSelector:` | NSException | `NSSetUncaughtExceptionHandler` ✅ |
| **野指针** | 访问已释放对象（Zombie 关掉后）| EXC_BAD_ACCESS → SIGSEGV/SIGBUS | signal handler ✅（需自回溯栈）|
| **Swift trap** | `fatalError` / 强解包 nil / 数组越界 | 运行时 trap → SIGTRAP / EXC_BREAKPOINT | **两个 handler 都接不到** ⚠️ |
| **主动退出** | `abort()`、断言、`exit()` | SIGABRT | signal handler ✅ |

> **一句话**：`NSSetUncaughtExceptionHandler` 只管 OC 异常；**Swift 的致命错误和内存崩溃都不走它**，所以自研方案一定还要挂 signal handler，而 OOM/Watchdog 这类「被系统杀」连崩溃日志都没有。

### 全部「handler 接不到」的终止情形（工作必背）

下面这些**进程被杀时你的 handler 根本没有机会执行**，崩溃采集只能靠系统日志/旁证：

| 终止情形 | 有没有 .ips | 信号/终止原因 | 特点与对策 |
|----------|-------------|---------------|------------|
| **OOM（JetSam）** | ❌ 无 | 系统直接 `SIGKILL` | 内存峰值超限；只留下系统级 OOM 记录，无堆栈。**近似手段**：Crashlytics 等用「上次非正常退出」标记；自己记录「上次启动时间 + 本次启动间隔」推断被杀 |
| **Watchdog（看门狗）** | ❌ 无（仅系统诊断）| `watchd` | 主线程卡主队列超时（前台约 20s / 后台更短）被 kill；无堆栈。**对策**：靠卡顿监控（见第九章）提前告警，别等 watchdog |
| **后台回收（Prior Kill）** | ❌ 无 | `prior kill` / `background*` | iOS 13+ 后台上滑/清理、后台冻结线程被回收；**不是 bug**，别当崩溃上报吓业务 |
| **用户手动上滑杀 App** | ❌ 无 | — | 用户主动行为，正常使用都会发生，必须从统计里排除（有 SDK 会标记「用户开始」）|
| **`kill -9` / SIGKILL** | ❌ 取决于时机 | 不可捕获 | SIGKILL **不可阻塞、不可忽略、不可捕获**；调试器、外部工具、系统回收都用它 |
| **`SIGTERM`（被杀）** | ❌ | 可被 handler 收到但默认终止 | 可捕获但通常来不及保存；HomeKit/后台任务被取消时常见 |
| **设备关机 / 重启 / 低电量断电** | ❌ 随机关 | — | 停机中断一切执行；崩溃分析按「启动前是否正常退出」判断 |
| **主线程死循环（不超时）** | ❌ 无 | 不触发任何信号 | 卡死但不崩 → 卡顿监控才看得到 |
| **handler 自身二次崩溃** | 可能丢原始现场 | handler 内非安全调用 | 原始崩溃现场被覆盖/丢失 → 见 13.8 坑 5 |
| **越狱 / 注入 / 被调试器 kill** | 可能有也可能无 | 各种 | 测试环境噪声，生产忽略 |

**快速判断口诀**：
- **有 .ips + Termination Reason = SIGNAL/EXC_** → 真崩溃，可以查
- **有 .ips + Termination Reason = prior kill/watchd/background** → 系统回收，不是 bug
- **完全没有 .ips** → OOM / 用户杀掉 / 关机 / SIGKILL，只配旁证

## 13.2 获取崩溃堆栈的四个层次

### 层次 1：系统 / Xcode 自带（开发期）

| 途径 | 操作 | 拿到什么 |
|------|------|----------|
| **Xcode Organizer** | Window → Organizer → Crashes | 已符号化崩溃聚合 |
| **Xcode Devices** | Window → Devices and Simulators → 设备 → View Device Logs | 原始 .ips |
| **CrashReporter 目录** | `~/Library/Logs/CrashReporter/*.ips`（Mac 侧）/ 真机设置里「分析数据」 | 原始崩溃报告 |
| **AirDrop 崩溃报告** | 真机  设置 → 隐私 → 分析与改进 → 分析数据 → 选 .ips → AirDrop 到 Mac | 原始报告 |

`.ips` 是 JSON 格式的崩溃报告，可直接拖进 Xcode 自动符号化。

### 层次 2：App Store Connect（线上免集成）

Xcode → Organizer → 你的 App → Crashes，Apple 汇总线上崩溃。优点：**零 SDK**；缺点：只有**接受共享的**用户数据、无自定义维度、延迟高。

### 层次 3：第三方 SDK（生产标配）

| SDK | 特点 |
|-----|------|
| **Firebase Crashlytics** | 市场主流，自动符号化、崩溃率看板、自定义 key |
| **Bugly（腾讯）** | 国内常用，符号表上传方便 |
| **Sentry** | 自托管/云，元数据丰富 |

原理都一样：**注册异常/信号 handler → 采集当前线程栈 → 本地暂存 → 下次启动上报 → 服务端用 dSYM 符号化**。

## 13.3 自研崩溃采集（OC 版完整原理）

### 13.3.1 捕获 OC 异常

```objc
// main.m 第一行就要注册（越早越好，启动崩溃才抓得到）
void UncaughtExceptionHandler(NSException *exception) {
    // ① 异常名 + 原因
    // exception.name / exception.reason
    // ② 堆栈：主线程的调用栈（文字版）
    NSArray<NSString *> *symbols = [exception callStackSymbols];
    // ③ 附带线程栈：使用 PLCrashReporter 或自写回溯
    // ④ 把数据同步写入本地文件（用 mmap/同步写，防止后续崩溃丢失）
    // ⑤ 不要在这个 handler 里做任何耗时/异步操作！
}
NSSetUncaughtExceptionHandler(&UncaughtExceptionHandler);
```

**注意**：
- `callStackSymbols` 给你的是**文字**堆栈（已含进程名偏移，未符号化），存下来后需要 address + dSYM 再做 `atos` 符号化
- handler 里**不要再抛异常回调**，否则死循环

### 13.3.2 捕获信号（内存类崩溃）

```objc
void SignalHandler(int sig) {
    // 注意：signal handler 上下文极其危险！
    // ✅ 能做：直接 write() 一段字节到文件（async-signal-safe）
    // ❌ 不能做：malloc / NSLog / objc 消息 / 加锁 / 拿 NSArray —— 全都不安全，会二次崩溃
    // 之后记录当前线程栈回溯结果，然后恢复默认 handler 并再次 raise，保持系统默认行为
    signal(sig, SIG_DFL);
    raise(sig);   // 恢复系统默认：正常生成 .ips、让崩溃能被系统捕获
}
signal(SIGABRT, SignalHandler);
signal(SIGSEGV, SignalHandler);
signal(SIGBUS,  SignalHandler);
signal(SIGILL,  SignalHandler);
signal(SIGFPE,  SignalHandler);
```

**⚠️ 为什么信号 handler 里不能调普通函数**：信号可能在任意代码执行到一半时插入（比如 malloc 内部），此时 malloc 的内部锁已被占用，你再去调 malloc 就**自己死锁/二次崩溃**。规范的做法是只有 `write()` 之类的 **async-signal-safe** 函数。

### 13.3.3 逐线程栈回溯（最重头）

`callStackSymbols` 只给**当前线程**；崩溃线程以外的线程（比如主线程被别的线程搞挂）也要收集：

- 崩溃线程：信号 handler 里直接拿到 `ucontext_t`，里面有寄存器现场，用 **frame pointer（FP）链**回溯：

```
FP 链回溯原理：
  FP（帧指针）→ 取出 [FP] 指向上一帧的 FP、[FP+8] 是返回地址 PC
  while (fp 合法) { 记录 PC；fp = *(fp) }
  每条线程的栈帧通过 FP 串联成链 = 一条调用栈
```

- 其他线程：`pthread_create` 时记录线程句柄名单，用 `thread_get_state` + `thread_suspend` 依次快照
- 栈帧边界：PC 落在 app 镜像的区间（用 `_dyld_image_count` + `_dyld_get_image_header/vmaddr_slide` 计算每个镜像 ±范围），用户态返回地址要减去 slide 才是 dSYM 里的地址

**成熟方案直接用 [PLCrashReporter](https://github.com/microsoft/plcrashreporter)**：内置 **Mach exception server**（比信号更早拦截，能拿到更完整的寄存器现场）+ 逐线程回溯 + 符号化一把梭，自研都是抄它的思路。

### 13.3.4 保存与上报

| 环节 | 坑点 |
|------|------|
| 存储 | handler 里**只能同步写**，禁止异步；先写临时文件再 rename（原子替换）|
| 上报时机 | **下次冷启动**时上报（崩溃现场网络可能不稳/磁盘受限），上报完删除 |
| 重试 | 断点续传 + 去重（按崩溃时间+堆栈 hash）|
| 必须字段 | app 版本、OS 版本、设备型号、时间、**剩余内存/磁盘**（判断 OOM 关键）|

## 13.4 Swift 崩溃捕获（双端差异重点 ⚠️）

### 13.4.1 Swift 崩溃根本不走 NSException

```swift
let arr = [1, 2]
let x = arr[5]          // ⚠️ 数组越界
```

- Swift 数组越界、强解包 nil、`fatalError`、`preconditionFailure`、`unowned` 悬垂 —— 全部是 **Swift runtime trap**，直接触发 **SIGTRAP（EXC_BREAKPOINT）**
- **不会发 NSException** → `NSSetUncaughtExceptionHandler` **一个都抓不到** ❌
- 所以 Swift 崩溃的兜底就是 **signal handler 里的 SIGTRAP** + 逐线程回溯

### 13.4.2 Swift 崩溃特征怎么识别

| 崩溃标记（.ips 里）| 含义 |
|------|------|
| `Exception Type: EXC_BREAKPOINT (SIGTRAP)` | 典型 Swift runtime trap（也见于断点）|
| `Exception Subtype: KERN_INVALID_ADDRESS` | 野指针（Swift 少见，OC/底层多）|
| `Termination Reason` 字段 | 区分用户崩溃 / 被系统杀（见 13.8）|
| 崩溃线程附近有 `swift_` 前缀符号 | Swift runtime 内部调用（demangled 后可读）|

### 13.4.3 Swift 侧采集要点

```swift
// 1) 信号 handler 用 C 函数，别写 Swift 闭包（Swift 闭包执行依赖 runtime，信号上下文里不可信）
// 2) 收集堆栈用 backtrace_symbols / 自写回溯，注意符号是 mangled 的：
//    _TTSg5__TSo8NSObjectC...  → 用 swift-demangle 还原成人类可读
// 3) Swift 崩溃现场的局部变量、寄存器恢复能力比 OC 差，
//    更依赖 dSYM + 符号化工具
// 4) 线上：Crashlytics 对 Swift 支持完善，优先用 SDK
```

### 13.4.4 OC 与 Swift 混编的隐藏炸弹

```objc
// OC 代码里 throw 一个 NSException，Swift 侧 try? 是【捕获不到】的
// Swift 的 do-catch 只处理 Swift Error，NSException 会直接沿栈往外崩
// → 混编项目里 OC 的异常边界必须自己兜（@try/@catch），别指望 Swift 兜
```

**混编面试一句话**：

> Swift 的 `fatalError`、数组越界、未解包崩溃走 SIGTRAP，OC 的 NSException 走 uncaught exception handler，两边互不相通；所以自研捕获要「双路监听」：异常 handler + 信号 handler（含 SIGTRAP），混编时 OC 抛的 NSException 在 Swift 侧 `try?` 接不住，只能在 OC 层兜。

## 13.5 崩溃链路全图（Mach → 信号 → handler 顺序）

```
程序异常
   ├─ NSException ──────────► NSSetUncaughtExceptionHandler（无则默认 abort → SIGABRT）
   └─ 内存访问错误 EXC_BAD_ACCESS
        ├─ Mach exception server（PLCrashReporter 挂这里，最底层）
        └─ 无 handler → 内核转 BSD 信号（SIGSEGV/SIGBUS）
             └─ signal handler（code 里注册的兜底）
                  └─ 无 handler → 系统默认动作：终止 + 生成 .ips
```

- 越靠底层越早拿到现场，但实现越复杂（Mach 层要伺候例外消息协议）
- 正常 App 里**不需要**同时装 Mach server 和 signal handler，CR 只选一个主通道
- 崩溃报告 .ips 只有「默认死了」才生成；**handler 里自己要处理好的事做完后恢复默认信号**，否则系统不生成官方报告

## 13.6 符号化：把地址变成函数名

### 13.6.1 三个关键事实

1. 崩溃堆栈默认是**十六进制地址 + 镜像名偏移**
2. **符号化必须用和崩溃包同一次构建的 dSYM**；每次构建 UUID 都变，不匹配=符号化失败
3. dSYM 里除了符号表，还带**行号**（DWARF）

### 13.6.2 工具链

```bash
# 1) 核对 UUID（必须与崩溃报告里的一致）
dwarfdump --uuid App.app.dSYM

# 2) 单条符号化
atos -o App.app.dSYM/Contents/Resources/DWARF/App -l 0x100000000 0x1000ab5c4

# 3) 批量：symbolicatecrash（Xcode 自带）
symbolicatecrash crash.ips App.app.dSYM -o readable.crash

# 4) CI 流程：xcodebuild 加配置自动生成并长久保存 dSYM
#    OTHER_DEBUG_INFO_OPTIONS / DEBUG_INFORMATION_FORMAT=dwarf-with-dSYM
```

### 13.6.3 Bitcode 的坑（老项目会遇到）

- 上传 **Bitcode** 的 App，商店侧的 dSYM 由 Apple 重新生成，**本地那份对不上** → 必须去 **App Store Connect → 我的 App → 活动 → 构建版本 → 下载 dSYM** 再符号化
- 新项目默认不勾 Bitcode（iOS 14+ 起 Apple 不再强制）

### 13.6.4 符号化失败自查表（实际工作中几乎全踩过）

| 现象 | 原因 | 解决 |
|------|------|------|
| `???` 函数名 | dSYM 缺失 / UUID 不匹配 | 找回同版本 dSYM；核对 UUID |
| 只有系统库符号 | 只符号化了 App 镜像，系统库本来就没 dSYM | 正常，iOS 符号由 Apple 提供 |
| 行号不对/没行号 | Release 优化（`-O` 内联、尾调用、strip）| 内联函数行号不可靠，属预期 |
| 地址对不上 | ASLR slide 没减 | 回溯时先减 `vmaddr_slide` 再交 atos |
| Swift 符号是乱码 | mangled 名 | atos / symbolicatecrash 会自动 demangle |

## 13.7 环境异常：磁盘 / 电量 / 温度 / 时间 / 弱网（采集韧性设计）

崩溃采集不只是「抓栈」，还要扛住**环境最差时刻**的考验——报告往往就是在环境最差时产生的。

### 磁盘空间不足（最容易被忽略）

| 场景 | 后果 | 对策 |
|------|------|------|
| 崩溃当场写报告 | handler 里 `write()` 失败 → **报告丢失** | 写入前查剩余空间；报告尽量小（<100KB）；先写临时文件再 rename |
| 系统自动清理 App **Caches** | 缓存、图片、`NSCache` 级数据全没 | 别把「需要持久」的数据放 Caches；被清后要能**重建/重新下载** |
| 日志模块自身写爆磁盘 | 日志堆积 → 用户卸载、App 变慢 | **日志轮转**：按大小（如 5MB）+ 按天数封顶；压缩并存 Caches |
| 沙盒 / DB 写入失败 | 业务数据损坏或丢失 | **所有持久化都检查返回值**；`NSData writeToFile:`、CoreData 错误分支必须处理 |
| 下载/缓存空间不足 | 下载中断，缓存写入失败 | 写前用「预计大小 vs 剩余空间」预检；失败走重试/降级 |

**检测剩余空间**（iOS 11+）：`NSURL.volumeAvailableCapacityForImportantUsage`（真可用空间，比 `attributesOfFileSystemForPath` 只读总空间更准）。

### 电量与温度

- **低电量模式**：系统压缩后台活动 → 后台上报延迟、BGTask 窗口变短
- **过热降频**：CPU 变慢 → 主线程更易卡 → **Watchdog 崩溃概率上升**（连起来看：温度高个月份崩溃率曲线会整体上移）
- **断电/异常关机**：写了一半的日志/crash 文件会**损坏** → 读取校验（文件头魔数 + CRC + 长度），坏的丢弃并计数

### 时间异常

- 用户改系统时间 → 崩溃时间戳错乱 → **按「启动序号/上报序」去重**，别只按时间戳 hash
- 日志轮转别依赖「最后修改时间」判断过期，用户手动改时间会让文件以为永远新鲜

### 弱网与上报队列

| 环节 | 做法 |
|------|------|
| 离线队列 | 上报失败入本地队列（限量，如 100 条，新报告优先）|
| 重试退避 | 1s → 2s → 4s → 8s 指数退避，别狂轰服务器 |
| 压缩 | gzip 后体积降 ~90%，弱网存活率大幅提升 |
| 上报时机 | 冷启动后 + 进入后台前（BGTaskScheduler 只给很短的窗口，别指望全量）|

## 13.8 工作中踩过的坑（重点 · 血泪清单）

### 坑 1：线上崩溃率高于崩溃日志数 —— OOM / Watchdog 没有日志

- **OOM（JetSam）**：内存峰值超限被系统干掉，**不产生 .ips**，Crashlytics 也记不清（它只能靠「上一次非正常退出」标记近似）
- **Watchdog**：主线程卡 > 20s（前后台阈值不同）被系统 kill，`Termination Reason = watchd`，同样没有堆栈
- 排查思路：**崩溃率 + 明显丢事件时，去看「卡顿监控」和内存峰值**，而不是死磕堆栈

### 坑 2：.ips 里写的是 `0x0` / 空栈 —— 检查「被系统杀」Prior Kill

- `.ips` 中 `Termination Reason`: `Namespace SIGNAL` 才是真崩溃；`Namespace: ...` 系统杀（`prior kill`、`background fetch`）**不是 bug**，别拿去吓业务
- 后台被系统挂起/回收很常见（iOS 15 以后后台行为更激进）

### 坑 3：启动崩溃采集不到 —— SDK 初始化太晚

- 崩溃发生在 `main()` 之前（`+load`、二进制里 `__attribute__((constructor))`）或 didFinishLaunching 前，SDK 还没注册 handler → 白丢
- 对策：**崩溃 SDK 必须在 main 第一行 / 最早期初始化**；启动路径上任何「可能崩」的代码先让 SDK 上线

### 坑 4：多个 SDK 互相覆盖异常 handler

- Bugly、Crashlytics 各自调 `NSSetUncaughtExceptionHandler`，后注册的覆盖先注册的 → 其中一个失去作用
- 对策：自定义 SDK 包装层，**保存旧 handler 并在新 handler 里链式调用**（`NSSetUncaughtExceptionHandler` 是一次性 setter，没有 getter，所以要自己存）

### 坑 5：signal handler 里写垃圾代码导致二次崩溃

- 在 SIGSEGV handler 里 NSLog / 调 `[NSDictionary dictionary]` / 加锁 → 立即二次崩溃，且覆盖原始现场
- 对策：handler 内只用 `write(fd, bytes, len)`；要 cat 字符串就**先在外面预备好 buffer**（static 数组）

### 坑 6：dSYM 没有归档 —— 三个月后找不回

- 线上用户还挂着老版本，崩溃堆栈需要**那一次构建**的 dSYM；CI 没自动归档 → 拿到报告无法符号化
- 对策：**CI 每次打包自动把 dSYM 存档（带版本+commit hash）并上传符号表服务**；本地开发机上的 dSYM 也会被 Xcode 清理

### 坑 7：测试包/模拟器崩溃污染数据

- 过滤：崩溃发生进程名含 `xctest`、`Simulator`、`UITesting` → 过滤掉
- 灰度/内测渠道单独分桶看

### 坑 8：「这次修复了没」判断不了 —— 缺乏版本对比

- 只看总量不看环比：新版本发布后崩溃量必然下降，可能只是用户少了
- 对策：看 **每千人崩溃率（crashes per 1000 sessions）** × 版本对比；堆栈 TOP10 单独看新版本占比

### 坑 9：Handler 里把崩溃报告「写丢了」

- 异步写（`dispatch_async`）在崩溃现场可能根本没执行完 → 丢报告
- mmap 映射文件先落盘、同步 write、写临时文件再 rename，三步保不丢

### 坑 10：野指针的「假复现」

- 关掉 Zombie 后崩溃只在低配/特定时机复现 → 加 **僵尸对象（Zombie）只在 Debug 开**，线上定位用 **malloc_log 类工具** + 「启用 Zombie 复现的堆栈」上报
- 堆栈本身可能「坏现场」：野指针地址读到哪算哪，符号可信但**调用顺序只能参考**，写根因报告时标注

### 坑 11：crash 不触发 NSSetUncaughtExceptionHandler 的例外

| 情形 | 真相 |
|------|------|
| Swift fatalError / 数组越界 | 走 trap，不走异常 handler（见 13.4）|
| abort() / assert | SIGABRT，走信号 |
| 被系统 kill（OOM/Watchdog/后台回收）| 两个 handler 都碰不到 |
| `fatalError` 到 `preconditionFailure` 之间多线程崩 | 也全是 trap，别期待 exception handler |

### 坑 12：把「被系统杀/用户杀」当崩溃算 —— 崩溃率虚高

- SDK 自带的统计数据里往往混合了 **Prior Kill、用户上滑、OOM 估算**，直接亮给老板/业务会虚高甚至「诡异的下降」
- 对策：**崩溃率口径 = 真崩溃（有堆栈且 Termination Reason 为信号/异常）÷ 活跃会话**；OOM/Watchdog 单独一条监控线，卡顿数、内存峰值分开看
- 判断「前一晚批量上报的都是同一型号 + 同一版本 + 时间集中」→ 多半是系统批量回收，先别急着发版

## 13.9 面试 30 秒版

> 崩溃分两条路：OC 异常走 `NSSetUncaughtExceptionHandler`（拿 `callStackSymbols`），Swift 的 trap 和野指针走信号（要自己逐线程回溯，handler 里只用 async-signal-safe 的 `write`）。自研方案的核心是「双路注册 + 栈回溯 + 下次启动上报」，成熟方案直接上 PLCrashReporter。拿到的是地址，要用**同 UUID 的 dSYM** 做 `atos` / `symbolicatecrash` 符号化；线上生产直接用 Crashlytics / Bugly。**最大的坑是没有日志的崩溃**：OOM、Watchdog 不产生堆栈，只能靠卡顿监控和内存指标侧面对齐；启动崩溃一定要让 SDK 最早初始化；dSYM 必须 CI 自动归档。

## 13.10 复习要点

1. 崩溃两条路：NSException（异常 handler）/ Mach→信号（signal handler）；Swift trap 两个都接不到
2. 自研捕获 = 双 handler + 逐线程 FP 回溯 + 原子落盘 + 下次启动上报
3. signal handler 里只能 `write()`，禁止 malloc/objc/加锁
4. 符号化三件套：UUID 匹配、dSYM、`atos`/`symbolicatecrash`；Bitcode 项目去 App Store Connect 下载 dSYM
5. **handler 接不到的终止全集**：OOM/Watchdog/后台回收/用户上滑/SIGKILL/关机 —— 无 .ips 或 Termination Reason 不是信号；只配旁证（内存峰值、卡顿、非正常退出标记）
6. 崩溃率口径：真崩溃（有堆栈+信号终止）÷ 活跃会话；OOM/Watchdog 单独监控
7. 工程纪律：SDK 最早初始化、CI 存 dSYM、版本对比看每千会话崩溃率
8. **环境韧性**：磁盘不足会丢报告/清 Caches；日志轮转防写爆；低电量/过热加剧 Watchdog；时间被改影响去重；上报走离线队列+退避+gzip
9. 混编：OC 的 NSException Swift 的 `try?` 接不住，需在 OC 层兜
10. 结合项目：说清自己项目的崩溃监控选型 + 一次线上崩溃的定位过程
