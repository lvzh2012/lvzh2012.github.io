# 第十二章：架构模式对比（MVC · MVVM · MVP · VIPER）

> **学习位置**：学完 [第十章 架构与项目实战](/posts/%E7%AC%AC%E5%8D%81%E7%AB%A0%E6%9E%B6%E6%9E%84%E4%B8%8E%E9%A1%B9%E7%9B%AE%E5%AE%9E%E6%88%98%E5%A4%A7%E5%8E%82%E9%AB%98%E9%A2%91-%E5%8E%9F%E7%90%86%E8%AF%A6%E8%A7%A3.html) 后阅读。本章是面试「架构题」的完整答法：模式有哪些、优缺点、怎么选。

## 12.1 全景对比

```
MVC（Apple 默认）     View ⇄ Controller → Model      职责简单，Controller 易膨胀
MVVM（主流）          View ⇄ ViewModel → Model       逻辑下沉，可测试，多一层
MVP（OC 时期）        View ⇄ Presenter → Model       每页一个 Presenter，双向通信
VIPER（大型项目）     View/Interactor/Presenter/Entity/Router  五层解耦，代码量大
```

| 模式 | 核心 | 数据流向 | 分层 | 测试性 | 学习成本 | 适合规模 |
|------|------|----------|------|--------|----------|----------|
| **MVC** | Controller 调度 | View→Controller→Model→View | 3 层 | 差（VC 难测） | ⭐ 低 | 小中型 |
| **MVVM** | ViewModel 承接逻辑 | View→ViewModel→Model（绑定） | 3 层 | 好（VM 可单测） | ⭐⭐ | 中型以上 |
| **MVP** | Presenter 驱动 | View→Presenter→Model→View（回调） | 3 层 | 好（P 可单测） | ⭐⭐ | 中型 |
| **VIPER** | 五层各司其职 | View→Presenter→Interactor→Entity | 5 层 | 极好 | ⭐⭐⭐⭐⭐ | 大型、多人 |

---

## 12.2 MVC 优缺点

```
User ──► Controller（输入处理）
            │ 更新
            ▼
          View ◄──── Model（数据 + 通知）
```

| 优点 | 缺点 |
|------|------|
| 职责分离清晰，易读 | **Controller 过重**：网络/解析/UI/导航全在 VC |
| 门槛低、上手快 | VC 几千行 → 难测、难复用、难维护 |
| Apple 官方默认，资料最多 | View 与 Controller 耦合强，难以独立复用 |
| 小项目开发效率最高 | 业务复杂时被迫堆代码，扩展性差 |

> 一句话：**MVC 是性价比最高的起点，但 Controller 是唯一出口，业务一多就膨胀**。

---

## 12.3 MVVM 优缺点

```
View（VC + View） ⇄绑定⇄ ViewModel ⇄ Model
                     │
                    Service（网络/DB）
```

| 优点 | 缺点 |
|------|------|
| **逻辑下沉到 VM**，VC 瘦身 | 多一层，小项目显得重 |
| **VM 可单元测试**（不依赖 UIKit） | 绑定复杂度高（KVO/Block/Combine 易出错） |
| VM 可复用（多端共享） | 双向绑定调试困难，出 bug 难定位 |
| 数据流单向清晰 | 过度设计时 VM 也会膨胀 |

> 一句话：**MVVM 用「多一层」换「可测试 + 可复用」**；绑定是它的核心也是它的坑。

---

## 12.4 MVP 优缺点

```
View ──► Presenter ──► Model
  ▲          │
  └──────────┘（回调刷新）
```

| 优点 | 缺点 |
|------|------|
| Presenter 纯逻辑，**可单测** | **双向通信**：View 与 Presenter 互相持有，回调多 |
| 职责比 MVC 更清晰 | 每页一个 Presenter，文件数量翻倍 |
| 视图逻辑可复用 | iOS 里 View 与 Controller 本为一体，分不干净 |
| 结构简单直观 | 处理异步/生命周期时代码繁琐 |

> 一句话：**MVP 靠 Presenter 把 UI 和逻辑彻底拆开，但双向依赖是它的软肋**。

---

## 12.5 VIPER 优缺点

```
Router ◄─► View ⇄ Presenter ⇄ Interactor ⇄ Entity（+ DataStore）
              （五层严格单向依赖，每层只管一件事）
```

| 优点 | 缺点 |
|------|------|
| **五层解耦**，模块边界清晰 | **代码量巨大**，一个页面十几个文件 |
| 每层可独立测试 | 学习成本高，新人不熟 |
| 适合大团队并行开发 | 简单功能也要走全套流程，**过度设计** |
| 职责单一，改动影响面小 | 调试需跨多层，上下文断裂 |

> 一句话：**VIPER 是「重型武器」，用代码量换工程化程度**，适合大型团队而非中小项目。

---

## 12.6 选型建议（面试答法）

| 场景 | 推荐 |
|------|------|
| 中小项目、逻辑简单 | **MVC**（快、够用） |
| 业务复杂、需要测试 | **MVVM**（iOS 主流答案） |
| 团队大、模块多、长线维护 | **VIPER**（或组件化 + MVVM） |
| 纯逻辑重度复用 | MVP / MVVM 皆可 |

**面试回答模板**：
> 小项目用 MVC 保证效率；业务复杂后切 MVVM，把逻辑下沉到 ViewModel 并绑定数据流，换来可测试性和可复用性；超大团队或模块化时再上 VIPER 或组件化。**架构没有银弹，跟着复杂度走。**

---

## 12.7 架构演化脉络（面试加分项）

**演化主线**：Controller/View 越来越薄 → 逻辑不断下沉 → 依赖越来越单向 → 测试性越来越强（代价是代码量上升）。

```
MVC（Apple 默认）───► Controller 膨胀（Massive View Controller）暴露
        │
        ├─ 抽逻辑到 Presenter（回调驱动）─────► MVP（OC 时代）
        │
        └─ 抽逻辑到 ViewModel + 绑定（替代回调）─► MVVM（RAC/Combine 推动，iOS 主流）
                                                      │
        Clean Architecture（依赖规则：依赖指向内层）──┤
                                                      │
                                                VIPER（2013，Clean 工程化，5 层）
                                                  ├─ 去 Router（导航难测）──► VIP
                                                  ├─ 只抽导航出 VC ──────────► Coordinator
                                                  ├─ 单向数据流（前端启发）──► Redux / Flux
                                                  ├─ 跨页组件化（Uber）─────► RIBs
                                                  └─ SwiftUI 时代（函数式）──► TCA
```

**演化驱动因素**：每一代都是解决上一代的痛点之一——① View/Controller 过重（→ MVP/MVVM）；② 模块边界不清、难测试、难并行（→ VIPER/VIP/TCA）。

**一句话背法**：MVC 是起点，MVVM 是主流，VIPER/VIP 是重型工程化，Redux/TCA 是状态驱动的单向流——**架构跟着业务复杂度走，没有银弹**。

---

## 12.8 其他模式变体一览

| 模式 | 一句话 | 与四大的关系 |
|------|--------|--------------|
| **VIP** | VIPER 去 Router（导航交给 UIKit 或单独层），3 层 | VIPER 精简版 |
| **Clean Architecture** | 依赖规则向内，业务核心与 UI/框架隔离 | 设计原则，可套在 MVVM/VIPER 上 |
| **Coordinator** | 导航逻辑从 VC 抽出独立管理层 | 常搭配 MVC/MVVM 使用 |
| **Redux / Flux** | 单向数据流：Action → Reducer → State → View | 状态驱动思想 |
| **TCA** | SwiftUI 函数式 + Redux（Reducer/Store/Effect） | 单向流 + 值类型，SwiftUI 团队热门 |
| **RIBs** | Uber 开源，跨页组件化 + 路由树 | 大型 App 组件化 |

## 12.9 高频 Q&A

### Q1：为什么 iOS 的 MVC 容易膨胀，Web 的 MVC 不会？

Web 的 Controller 只管「请求→响应」，状态和视图都轻；iOS 的 View 状态不可序列化，一切输入输出都要 Controller 中转，所以 Controller 天然承重。

### Q2：MVVM 里 ViewModel 为什么不 import UIKit？

保持 VM 与视图无关才能**脱离 UI 单测**；一旦 VM 持有 View，就退化成 MVC 的 Controller。

### Q3：VIPER 和 MVVM 怎么选？

人数 < 10 或迭代快 → MVVM；模块多、要长期并行开发、有独立 QA → VIPER。VIPER 的本质是「用工程约束替代个人自觉」。

### Q4：三种模式可以混用吗？

可以。实际项目常是 **MVC + 局部 MVVM**（列表页 VM 化）或 **组件化 + 各组件内部 MVVM**。面试说「按复杂度分层使用」比「只会一种」加分。
