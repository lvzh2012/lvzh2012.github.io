# 第五章：多线程面试八股

## 5.1 为什么需要多线程？

| 目的 | 说明 |
|------|------|
| **提升体验** | 耗时操作放子线程，主线程保持 UI 流畅（60fps ≈ 16.7ms/帧） |
| **充分利用 CPU** | 多核并行处理 |
| **同时处理 I/O** | 网络、磁盘读写不阻塞 UI |

**铁律**：**UI 更新必须在主线程**。

---

## 5.2 iOS 多线程方案对比

| 方案 | 特点 | 使用场景 |
|------|------|----------|
| **NSThread** | 轻量、手动管理生命周期 | 几乎不用，了解即可 |
| **GCD** | C API、轻量、系统底层 | **最常用**，异步任务 |
| **NSOperation** | 面向对象、可取消、依赖、KVO | 复杂任务编排 |
| **pthread** | POSIX 标准、C 语言 | 底层库，App 层少见 |

**面试结论**：日常 **GCD 为主**，需要取消/依赖/进度时用 **NSOperation**。

---

## 5.3 GCD 核心概念

### 进程 / 线程 / 任务 / 队列（先分清四个概念）

#### 一句话定义

| 概念 | 是什么 | 类比 |
|------|--------|------|
| **进程** | 资源分配的最小单位：独立的虚拟地址空间、代码、数据 | 一家公司 |
| **线程** | CPU 调度执行的最小单位，**共享进程内内存** | 公司里的员工 |
| **任务** | 一段待执行的代码（block / 函数），排进队列等调度 | 工单 |
| **队列** | 任务的容器：管 FIFO 排队方式 + 串行/并发规则 | 工单分发台 |

```objc
// 任务 = 一个 block；队列 = 分发给它的调度规则；最终在某个线程上执行
dispatch_async(serialQueue, ^{ /* 这就是一个任务 */ });
```

#### 进程 vs 线程（面试必背）

| 维度 | 进程 | 线程 |
|------|------|------|
| 资源 | 独立虚拟地址空间、句柄、隔离 | **共享**进程内堆、代码、数据 |
| 调度 | 系统按进程管理 | CPU 按线程调度 |
| 切换成本 | 高（页表、缓存失效）| 低（栈切换）|
| 崩溃 | 进程崩不影响其他进程 | **线程崩 = 整个进程崩** |
| iOS 视角 | 一个 App 通常一个进程（沙箱隔离）| 主线程 + GCD 线程池（复用）|

- **进程是隔离的**：A 进程奔溃不拖垮 B 进程；**线程是共享的**：共享同一块堆内存 —— 所以才有线程安全问题
- **线程间通信比进程间通信便宜**：同进程内直接读写共享内存即可；跨进程要 NSXPC / XPC / URLScheme

#### 任务 vs 队列 vs 线程（谁是谁的什么）

```
任务（block）──提交──► 队列（排期）──派发──► 线程池 worker（执行）
     ↑ 你只负责生成任务               ↑ 队列只负责排                             ↑ 真正干活的不是任务/队列
```

- **任务不知道自己在哪跑**：同一个 block 这次在 worker1、下次可能在 worker2
- **队列不知道谁来跑**：它只管"何时可以执行 + 能否并行"
- **线程不持有队列**：串行队列的任务也能在两条不同线程上先后执行

#### 同步 vs 异步（区分的是「调用方等不等」）

| | 同步（sync）| 异步（async）|
|--|------------|--------------|
| 调用方 | **阻塞等待任务完成**才返回 | **提交后立即返回**，继续干自己的 |
| 任务在哪执行 | 通常就在调用方线程就地执行 | 必在其他 worker 线程 |
| 怎么拿结果 | 返回值直接给 | 回调 / 信号量 / 通知 |
| GCD 例子 | `dispatch_sync` | `dispatch_async` |

**误区**：
- 同步 ≠ 单线程 ❌（sync 只是"调用方等"，任务间仍可并行）
- 异步 ≠ 新开线程 ❌（可能复用线程池已有线程）
- "同步/异步"永远站在**调用方**视角；"串行/并发"站在**队列**视角，两两正交：

```
            调用方视角（等不等）         队列视角（并行不并行）
sync    ── 等任务完成 ←───────────┐
async   ── 不等，转身就走          ├── 串行：一次一个；并发：可同时多个
                                 ┘
```

**面试一句话**：

> 进程 = 资源隔离的最小单位，线程 = CPU 执行的最小单位；任务放进队列排队，由线程池执行；同步 = 调用线程等到任务完成，异步 = 提交即走、完成在别处；串行/并发是队列的属性，同步/异步是调用方与任务的关系，二者正交 —— 组合可得到「并发队列 + async」「串行队列 + sync」等四种用法。

### 队列类型

| 队列 | 说明 |
|------|------|
| **主队列** `dispatch_get_main_queue()` | 串行，主线程，UI 专用 |
| **全局并发队列** `dispatch_get_global_queue()` | 系统提供，并发 |
| **自定义串行队列** | 自己创建，任务顺序执行 |
| **自定义并发队列** | 自己创建，多任务并行 |

### 任务提交方式

| API | 行为 |
|-----|------|
| `dispatch_async` | **异步**，不阻塞当前线程 |
| `dispatch_sync` | **同步**，等任务执行完才返回 |

```objc
// 子线程做耗时，主线程刷 UI
dispatch_async(dispatch_get_global_queue(DISPATCH_QUEUE_PRIORITY_DEFAULT, 0), ^{
    NSData *data = [self loadData];
    dispatch_async(dispatch_get_main_queue(), ^{
        self.imageView.image = [UIImage imageWithData:data];
    });
});
```

### QoS 优先级（从高到低）

`userInteractive` → `userInitiated` → `default` → `utility` → `background`

### 队列与线程的关系（易混淆 ⚠️）

先记 **一句话**：

> **队列（Queue）= 任务排队规则；线程（Thread）= 真正干活的 CPU 执行单元。**  
> GCD **把 block 丢进队列**，由系统 **线程池** 取任务执行；**不要** 默认「一个队列 = 一条线程」。

#### 关系对照

| 概念 | 是什么 | 谁管 |
|------|--------|------|
| **队列** | 任务的 FIFO 调度结构 + **串行/并发** 语义 | GCD / NSOperationQueue |
| **线程** | 内核调度的执行流 | 系统线程池（GCD 复用） |
| **主队列** | **串行队列**，且 **绑定主线程** | 特例：任务一定在主线程跑 |
| **全局并发队列** | 系统提供的 **并发队列** | 任务可在 **多条**  worker 线程并行 |
| **自定义串行队列** | 同一时刻 **只执行 1 个** block | 可能在 **线程 A** 跑完 task1，又在 **线程 B** 跑 task2 |
| **自定义并发队列** | 可同时执行多个 block | 由 GCD 决定开几条线程（有上限，非无限） |

```
你写的 block  →  dispatch_async(queue, ^{ ... })
                      ↓
                 进入 queue 排队
                      ↓
              GCD 线程池取出执行（哪条线程由系统决定）
```

#### 串行队列 ≠ 单线程（最高频误区）

```objc
dispatch_queue_t serialQ = dispatch_queue_create("com.demo", DISPATCH_QUEUE_SERIAL);

dispatch_async(serialQ, ^{
    NSLog(@"task1 %@", [NSThread currentThread]);  // 可能是 <NSThread: 0x600...>{number = 3}
});
dispatch_async(serialQ, ^{
    NSLog(@"task2 %@", [NSThread currentThread]);  // 可能是 <NSThread: 0x600...>{number = 7}
});
// ✅ task1、task2 顺序执行（串行）
// ❌ 但不保证是同一条线程
```

**串行** 保证的是 **任务顺序**，不是 **线程固定**。

#### 并发队列 ≠ 一定开 N 个线程

- 并发队列 = **允许** 多个 block **同时** 执行
- 实际并行度受 **CPU 核数、QoS、系统负载** 限制，不会无限开线程
- `dispatch_apply` 遍历 10000 次也不会开 10000 线程

#### async / sync 混淆的是「谁阻塞」

| API | 当前 **调用线程** | 任务何时跑 |
|-----|-------------------|------------|
| `dispatch_async` | **不阻塞**，提交后立即返回 | 稍后由队列调度 |
| `dispatch_sync` | **阻塞**，等 block 跑完才返回 | 尽快在当前/其他 worker 上执行 |

```objc
// 在子线程
NSLog(@"1");
dispatch_async(queue, ^{ NSLog(@"3"); });
NSLog(@"2");
// 输出顺序：1 → 2 → 3

NSLog(@"A");
dispatch_sync(queue, ^{ NSLog(@"B"); });
NSLog(@"C");
// 输出顺序：A → B → C（当前线程被 sync 卡住）
```

**误区**：`async` = 新开线程 ❌ → 只是 **异步入队**，线程由 GCD 分配（可能复用线程池）。

#### 主队列 vs 主线程

| | 主队列 | 主线程 |
|--|--------|--------|
| 关系 | `dispatch_get_main_queue()` **绑定** 主线程 | UI、RunLoop 所在 |
| 串/并 | **串行** | — |
| 从子线程 `async(main)` | block 回主线程执行 | ✅ |
| 在主线程 `sync(main)` | 等主队列 → 自己等自己 | ❌ **死锁** |

#### GCD 队列 vs NSOperationQueue

| | GCD | NSOperationQueue |
|--|-----|------------------|
| 本质 | C API，轻量 | 面向对象，封装 GCD |
| 并发控制 | 队列类型 + barrier | `maxConcurrentOperationCount` |
| 取消/依赖 | 无原生 cancel | ✅ `cancel`、依赖链 |
| 主队列 | `dispatch_get_main_queue()` | `[NSOperationQueue mainQueue]`（底层仍走 GCD） |

#### 其他易混点

| 说法 | 正误 | 说明 |
|------|------|------|
| 「串行队列安全，不用加锁」 | ⚠️ | 只保证 **该队列上的 block** 不并行；若 **多个队列/线程** 同时访问同一变量仍不安全 |
| 「全局队列是后台线程」 | ❌ | 是 **并发队列** + QoS；`DISPATCH_QUEUE_PRIORITY_BACKGROUND` 才偏后台 |
| `dispatch_get_current_queue()` | 已废弃 | 别用；调试可用断点 / Instruments |
| 常驻线程 vs 串行队列 | 易混 | 要 **RunLoop/Timer/onThread** → 线程；只要 **顺序执行异步任务** → 串行队列够用 |
| URLSession 回调队列 | — | `delegateQueue` 指定 **队列**，回调 block 在该队列关联的线程执行 |

#### 面试 30 秒版

> 队列管 **怎么排任务**（串行一次一个、并发可多个），线程管 **在哪执行**。主队列绑定主线程；自定义串行队列 **顺序执行但不绑死一条线程**；GCD 用线程池，`async` 不阻塞调用方，`sync` 会阻塞且对同串行队列易死锁。

## 5.4 GCD 死锁（必考 ⚠️）

### 经典死锁：主队列 sync

```objc
// ❌ 必死锁
dispatch_sync(dispatch_get_main_queue(), ^{
    // 主队列等主队列，互相等待
});
```

### 串行队列 sync 自己

```objc
dispatch_queue_t queue = dispatch_queue_create("com.test", DISPATCH_QUEUE_SERIAL);
dispatch_async(queue, ^{
    dispatch_sync(queue, ^{  // ❌ 同一串行队列 sync 自己 → 死锁
    });
});
```

### 死锁条件总结

> **当前队列** 对 **同一串行队列** 调用 `dispatch_sync`，且该 sync 任务需要等当前任务结束 → 互相等待。

### 并发队列 sync 自己

```objc
// ✅ 不会死锁，但会开新线程执行（不推荐这样写）
dispatch_queue_t concurrentQ = dispatch_queue_create("c", DISPATCH_QUEUE_CONCURRENT);
dispatch_async(concurrentQ, ^{
    dispatch_sync(concurrentQ, ^{ /* OK */ });
});
```

## 5.5 GCD 常用 API

| API | 用途 |
|-----|------|
| `dispatch_group` | 等多任务全部完成 |
| `dispatch_barrier` | 并发队列中「写屏障」，读写锁语义 |
| `dispatch_semaphore` | 信号量，控制并发数 / 线程同步 |
| `dispatch_once` | **单例** 线程安全初始化 |
| `dispatch_after` | 延迟执行（不保证精确时间） |
| `dispatch_apply` | 并发遍历（注意控制并发度） |

### dispatch_group 示例

```objc
dispatch_group_t group = dispatch_group_create();
dispatch_group_enter(group);
dispatch_async(queue, ^{
    // task A
    dispatch_group_leave(group);
});
dispatch_group_enter(group);
dispatch_async(queue, ^{
    // task B
    dispatch_group_leave(group);
});
dispatch_group_notify(group, dispatch_get_main_queue(), ^{
    // A、B 都完成，回主线程
});
```

### dispatch_once 单例

```objc
+ (instancetype)shared {
    static id instance = nil;
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        instance = [[self alloc] init];
    });
    return instance;
}
```

### dispatch_semaphore 限制并发数

```objc
dispatch_semaphore_t sem = dispatch_semaphore_create(3); // 最多 3 个并发
dispatch_semaphore_wait(sem, DISPATCH_TIME_FOREVER);
// 执行任务
dispatch_semaphore_signal(sem);
```

### dispatch_barrier 多读单写（读写锁）— 必考 ⚠️

#### 标准答案（面试直接背这份）

```objc
@interface HACache ()
@property (nonatomic, strong) dispatch_queue_t queue;   // 私有并发队列（必须自己创建）
@property (nonatomic, strong) NSMutableDictionary *dic;
@end

@implementation HACache

- (instancetype)init {
    if (self = [super init]) {
        _queue = dispatch_queue_create("cache.queue", DISPATCH_QUEUE_CONCURRENT);
        _dic = [NSMutableDictionary dictionary];
    }
    return self;
}

// 写：barrier + async → 写之间、读写之间互斥，且不阻塞调用方（主线程不卡）
- (void)setObject:(id)value forKey:(NSString *)key {
    NSParameterAssert(key && value);
    dispatch_barrier_async(self.queue, ^{
        self.dic[key] = value;
    });
}

// 读：普通 sync → 读与读可并行；必须 sync 才能拿返回值
- (id)valueOfKey:(NSString *)key {
    NSParameterAssert(key);
    __block id value = nil;
    dispatch_sync(self.queue, ^{
        value = self.dic[key];
    });
    return value;
}
@end
```

#### 设计原则（背这两行）

| 操作 | 用什么 | 为什么 |
|------|--------|--------|
| **写** | `barrier_async` | barrier 串行化写、隔离前后读写；`async` 不阻塞调用方线程 |
| **读** | 普通 `sync` | 读之间可并行；必须 `sync` 阻塞拿返回值 |

#### barrier 的两层语义（FIFO 时序）

```
t0  读A 入队 ─────┐
t1  读B 入队 ──┐  │  ① barrier 执行前：等所有「先提交」的任务完成
t2  写C 入队(BARRIER)◄──┘
t3  读D 入队 ────────►  ② barrier 执行中：后提交的任务被拦截，等 C 完成才放行
```

- ① 等的是**排在它前面**的任务，不是「队列里所有任务」（t3 在它后面，不归它等）
- ② barrier 结束时**拦截后续任务**到它跑完
- 由此保证：读并发、写互斥、读写永不交叉

#### 为什么不能把 barrier 换成 / 用错地方（四版错误正反例）

| 版本 | 写 | 读 | 结论 |
|------|----|----|------|
| v1 | barrier_sync | barrier_sync | 读不该 barrier：所有读被串行化，性能=串行队列 |
| v2 | 普通 sync | barrier_sync | **最严重**：写无保护，两个写并发改字典 → 崩溃 |
| v3 | barrier_sync | 普通 sync | 方向全对，仅剩：写应换 `async`（否则主线程调 set 会卡） |
| v4 | barrier_sync | **async** | **读拿不到值**：async 提交后立刻 return，`value` 还是 nil |

v4 的时序：方法 `return value` 时 block 还在后台排队 → 永远返回 nil；想异步只有改回调风格，否则读必须 sync。

#### 大坑：全局队列上 barrier 会失效

```objc
// ❌ 没用的写法：barrier 只在「自定义并发队列」上生效
dispatch_barrier_async(dispatch_get_global_queue(0, 0), ^{ ... });
```

- Apple 文档：barrier 提交到全局并发队列时**退化成普通 block**，互斥消失
- 全局队列全 App 共享，无法独占，互斥范围不可控
- 所以读写锁必须配**私有并发队列**；全局队列只适合不关心互斥的通用任务

#### sync/async 与 barrier 的三个高频追问

| 追问 | 答案 |
|------|------|
| `sync` 会阻塞谁？ | 阻塞**调用方线程**（与队列串/并无关），直到 block 执行完 |
| 写为什么用 async？ | `barrier_sync` 会让调用方等「队列里所有先提交任务完成」，主线程调 set → 卡 UI |
| 并发队列 + sync 会在哪执行？ | GCD 优化：block 尽量在**调用方线程**直接执行（省线程切换），所以 v2 里两个写真的会同时跑 |

**死锁红线**：在同一队列的 block 内部再 `sync` 同一队列 → 死锁（串行队列必死锁，并发队列虽不死锁但别这么写）。

#### 面试 30 秒版

> 读写锁 = 私有并发队列 + 写 `barrier_async` + 读普通 `sync`。barrier 有两层语义：等前面任务完成、执行时拦住后面任务；只在自定义并发队列生效（全局队列退化为普通 block）。写用 async 是不阻塞主线程，读用 sync 是为了拿返回值。

## 5.6 NSOperation / NSOperationQueue

| 特性 | GCD | NSOperation |
|------|-----|-------------|
| 取消任务 | 难 | ✅ `cancel` |
| 任务依赖 | 需 group 等 | ✅ `addDependency:` |
| KVO 进度 | 无 | ✅ `NSProgress` |
| 优先级 | QoS | `queuePriority` |
| 最大并发 | 队列控制 | `maxConcurrentOperationCount` |

```objc
NSBlockOperation *op1 = [NSBlockOperation blockOperationWithBlock:^{ /* A */ }];
NSBlockOperation *op2 = [NSBlockOperation blockOperationWithBlock:^{ /* B */ }];
[op2 addDependency:op1];  // B 等 A 完成

NSOperationQueue *queue = [[NSOperationQueue alloc] init];
[queue addOperations:@[op1, op2] waitUntilFinished:NO];
```

**底层**：NSOperationQueue 通常 **基于 GCD 实现**。

## 5.7 线程安全

### 线程安全问题类型

| 问题 | 说明 |
|------|------|
| **竞态条件** | 多线程同时读写，结果依赖执行顺序 |
| **死锁** | 互相等待锁 |
| **优先级反转** | 低优先级持锁，高优先级等待 |

**举个例子（经典三线程）**：

```
优先级：H（高，如音频/UI 实时线程）> M（中，如网络解析）> L（低，如日志/清理）

① L 拿到锁 lock，正在执行临界区
② H 也需要 lock → 阻塞，等 L 释放
③ 调度器去跑 M（M 比 L 高，L 抢不到 CPU）
④ M 一直占着 CPU，L 跑不完 → 锁不释放 → H 一直等

结果：最高优先级的 H 被最低优先级的 L 间接「拖死」——优先级形同反转
```

**iOS 真实案例**：早期 **`OSSpinLock`** 自旋等待时不做优先级继承，高优先级线程空转占 CPU，低优先级持锁线程反而跑不起来，所以 Apple **废弃 SpinLock**，改用 **`os_unfair_lock`**（支持优先级继承）。

**解决**：优先级继承（Priority Inheritance）——当 H 在等 L 的锁时，系统**临时把 L 提升到 H 的优先级**，让 L 尽快执行完释放锁；GCD 串行队列、`pthread_mutex`（部分配置）、`os_unfair_lock` 均涉及此机制。

### 常见锁

| 锁 | 特点 |
|----|------|
| `@synchronized(obj)` | 简单，性能一般 |
| **`NSLock` / `NSRecursiveLock`** | 递归锁可重入 |
| **`pthread_mutex`** | 底层互斥锁 |
| **`OSSpinLock`** | 自旋锁，**已废弃**（优先级反转） |
| **`os_unfair_lock`** | 替代 SpinLock，轻量 |
| **`dispatch_semaphore`** | 信号量 |
| **`dispatch_barrier`** | 多读单写 |
| **`@atomic`** | 只保证 setter/getter **原子**，不保证整体线程安全 |

### atomic vs nonatomic

```objc
@property (atomic, strong) NSMutableArray *list;
// atomic：getter/setter 单次读写原子
// 但 thread1 读 + thread2 写 + thread1 改 仍不安全！
// 线程安全需：串行队列 / 锁 / 不可变设计
```

#### Demo 1：多线程同时 `addObject:`（最常见）

`atomic` 只保证 **`self.list = xxx` 赋值** 原子，**不保证** 对取出来的 `NSMutableArray` 做 `addObject:` 原子。

```objc
@interface DemoVC ()
@property (atomic, strong) NSMutableArray *list;
@end

@implementation DemoVC

- (void)viewDidLoad {
    [super viewDidLoad];
    self.list = [NSMutableArray array];

    dispatch_group_t group = dispatch_group_create();
    for (int t = 0; t < 2; t++) {
        dispatch_group_async(group, dispatch_get_global_queue(QOS_CLASS_DEFAULT, 0), ^{
            for (int i = 0; i < 10000; i++) {
                [self.list addObject:@(i)];  // ❌ 非原子：读指针 + 改内部结构
            }
        });
    }
    dispatch_group_notify(group, dispatch_get_main_queue(), ^{
        // 期望 20000，实际常 < 20000，甚至 EXC_BAD_ACCESS 崩溃
        NSLog(@"count = %lu", (unsigned long)self.list.count);
    });
}

@end
```

**原因**：`addObject:` 等价于「拿到数组指针 → 改内部存储」，两步之间另一线程也在改，**`NSMutableArray` 本身非线程安全**。

#### Demo 2：读-改-写丢失更新

```objc
// 两个线程都执行下面这段（atomic 救不了整段逻辑）
NSMutableArray *snapshot = self.list;           // ① atomic getter
NSMutableArray *next = [snapshot mutableCopy];  // ② 基于旧快照拷贝
[next addObject:@(arc4random())];               // ③ 各自改各自的
self.list = next;                                 // ④ atomic setter，后写覆盖先写

// 各加 10000 次，期望 10000，实际往往只有 ~5000～8000（另一线程的写入被覆盖）
```

**原因**：`atomic` 保证 ① 和 ④ **各自** 不被打断，但 **①→④ 整段不是事务**，两线程可能基于同一份旧 `list` 各自写回，**丢更新**。

#### 正确写法（择一）

```objc
// 方案 A：串行队列保护所有读写
@property (nonatomic, strong) NSMutableArray *list;
@property (nonatomic, strong) dispatch_queue_t listQueue;

- (void)safeAddObject:(id)obj {
    dispatch_async(self.listQueue, ^{
        [self.list addObject:obj];
    });
}

// 方案 B：不可变 + 整体替换（仍要配合队列/锁）
// self.list = [[self.list arrayByAddingObject:obj] copy];
```

**面试标准答法**：

> `atomic` 只保证 **属性赋值操作** 不会被线程打断，**不等于** 对象内部业务逻辑线程安全。

## 5.8 多线程 + RunLoop

> RunLoop 与触摸事件的关系见 [第七章 扩展八股](/posts/%E7%AC%AC%E4%B8%83%E7%AB%A0%E6%89%A9%E5%B1%95%E5%85%AB%E8%82%A1%E5%86%85%E5%AD%98-runloop-%E5%85%B3%E8%81%94%E7%9F%A5%E8%AF%86%E7%82%B9.html)、[Common 第六章 Hit-Testing](/posts/%E7%AC%AC%E5%85%AD%E7%AB%A0%E4%BA%8B%E4%BB%B6%E4%BC%A0%E9%80%92%E9%93%BEhit-testing.html)。

| 线程 | RunLoop |
|------|---------|
| **主线程** | 默认开启，处理 UI、Timer、Source |
| **子线程** | **默认没有**，需要手动 `run`（如常驻线程） |

```objc
// 常驻线程典型写法
- (void)threadEntry {
    @autoreleasepool {
        NSRunLoop *runLoop = [NSRunLoop currentRunLoop];
        [runLoop addPort:[NSPort port] forMode:NSDefaultRunLoopMode];
        [runLoop run];  // 不会返回，保持线程存活
    }
}
```

### 常驻线程：投递长任务 & 任务结束后如何退出？

**分清两件事**：

| 目标 | 做法 |
|------|------|
| 长任务跑完，**线程继续复用** | 用 `performSelector:onThread:` / 自定义 Source 把任务丢进 RunLoop，**不要** `CFRunLoopStop` |
| 长任务跑完，**线程也销毁** | 在该线程内（或 `waitUntilDone` 派发到该线程）调用 **`CFRunLoopStop`**，让 `[runLoop run]` 返回 |

`[runLoop run]` **自己不会结束**，必须有人调 `CFRunLoopStop(CFRunLoopGetCurrent())`（且最好在 **目标线程** 上调用）。

#### 推荐写法：可停止的常驻线程

```objc
@interface WorkerThread : NSObject
@property (nonatomic, strong) NSThread *thread;
@property (nonatomic, strong) NSPort *keepAlivePort;
@property (atomic, assign) BOOL stopped;
@end

@implementation WorkerThread

- (void)start {
    self.stopped = NO;
    self.thread = [[NSThread alloc] initWithBlock:^{
        [self threadEntry];
    }];
    [self.thread start];
}

- (void)threadEntry {
    @autoreleasepool {
        NSRunLoop *runLoop = [NSRunLoop currentRunLoop];
        self.keepAlivePort = [NSPort port];
        [runLoop addPort:self.keepAlivePort forMode:NSDefaultRunLoopMode];

        // 用 runMode 循环，便于配合 CFRunLoopStop 退出
        while (!self.stopped && [runLoop runMode:NSDefaultRunLoopMode
                                     beforeDate:[NSDate distantFuture]]) {}

        [runLoop removePort:self.keepAlivePort forMode:NSDefaultRunLoopMode];
    }
    // 出了 threadEntry，线程结束
}

/// 在该常驻线程上执行长任务（跑完线程仍存活，可继续投递下一个任务）
- (void)performTask:(dispatch_block_t)task {
    [self performSelector:@selector(runTask:)
                 onThread:self.thread
               withObject:task
            waitUntilDone:NO];
}

- (void)runTask:(dispatch_block_t)task {
    @autoreleasepool {
        if (task) task();   // 长时间任务放这里
    }
    // 不调用 CFRunLoopStop → 线程继续等下一个任务
}

/// 停止常驻线程（任务是否还在跑，需业务自己保证先 cancel 任务）
- (void)stop {
    self.stopped = YES;
    [self performSelector:@selector(stopRunLoop)
                 onThread:self.thread
               withObject:nil
            waitUntilDone:YES];  // 等 threadEntry 完全退出
}

- (void)stopRunLoop {
    CFRunLoopStop(CFRunLoopGetCurrent());  // 必须在目标线程调
}

@end
```

#### 长任务完成后「连线程一起关掉」

在 `runTask:` 末尾加一行即可：

```objc
- (void)runTaskAndFinish:(dispatch_block_t)task {
    @autoreleasepool {
        if (task) task();
    }
    CFRunLoopStop(CFRunLoopGetCurrent());  // [runLoop run] / runMode 循环退出，线程结束
}
```

#### 长任务中途取消

RunLoop **不会**自动 cancel 你的业务代码，需要 **协作式取消**：

```objc
@property (atomic, assign) BOOL taskCancelled;

- (void)longTask {
    for (NSInteger i = 0; i < huge; i++) {
        if (self.taskCancelled) break;  // 任务内轮询
        // ...
    }
}

- (void)cancelTask {
    self.taskCancelled = YES;
}
```

若任务卡在阻塞 IO，还要 **close socket / cancel NSURLSessionTask** 等，单靠 `CFRunLoopStop` 不够。

#### 工程建议（2026 常见做法）

| 需求 | 更推荐 |
|------|--------|
| 串行后台任务 | **GCD 串行队列** / `OperationQueue` |
| 定时、Source | 常驻线程 + RunLoop（AFNetworking 2.x 时代常见） |
| 一次性长任务 | `dispatch_async` 即可，**不必**常驻线程 |

**关联**：

- `performSelector:onThread:` 目标线程需 RunLoop
- `NSTimer` 依赖 RunLoop
- 网络回调线程取决于 API 设计（NSURLSession delegate 队列可指定）

## 5.9 常见坑

| 坑 | 说明 |
|----|------|
| 子线程更新 UI | 崩溃或未定义行为，必须 `dispatch_async(main)` |
| 主队列 sync | 死锁 |
| `dispatch_after` 当 Timer | 不精确，Block 捕获可能循环引用 |
| 过度创建线程 | GCD 有线程池，不必自己 NSThread 满天飞 |
| 锁粒度太大 | 性能差；太小可能死锁 |
| `@synchronized(self)` 锁 self | self 被多处锁可能死锁，建议专用 token 对象 |

## 5.10 面试 Q&A

### Q1：GCD 串行 vs 并发队列？

- **串行**：同一时刻只执行一个任务，顺序 FIFO
- **并发**：可多个任务同时执行（由 GCD 线程池调度）

### Q2：`dispatch_async(main)` 一定在主线程吗？

在 **子线程** 调用 → block **异步** 到主队列，在主线程执行。  
调用时 **已在主线程** → block 可能 **直接在当前主线程** 执行（不另开线程，仍算 async 语义）。

### Q2b：串行队列是不是只有一条线程？

**不是。** 串行只保证 **任务按顺序一个接一个**；不同任务可能在 **不同 worker 线程** 上跑（GCD 线程池复用）。

### Q3：如何实现线程安全的单例？

`dispatch_once` — 系统保证 block 只执行一次，且线程安全。

### Q4：读写锁怎么实现？

**私有并发队列** + 写 barrier + 读普通 sync（完整代码见 [5.5 barrier 详解](#dispatch_barrier-多读单写读写锁--必考-))：

- 写：`dispatch_barrier_async` → 写互斥、不阻塞调用方
- 读：`dispatch_sync` → 读可并行、阻塞拿返回值（**不能用 async**，否则拿不到值）
- ⚠️ barrier 只对 **自定义并发队列** 生效，全局队列上退化为普通 block

### Q5：GCD 和 NSOperation 怎么选？

- 简单异步 → GCD
- 需取消、依赖、进度 → NSOperation
- AFNetworking 早期用 NSOperation，现多用 GCD + 封装

### Q6：以下会死锁吗？

```objc
dispatch_queue_t q = dispatch_queue_create("s", DISPATCH_QUEUE_SERIAL);
dispatch_async(q, ^{
    NSLog(@"1");
    dispatch_sync(q, ^{
        NSLog(@"2");  // ❌ 死锁
    });
});
```
